## Намір і критерії

Показати, що відбувається в кожному сценарії обраного UC з більшою деталізацією стосовно дій системи. 
Критерії: окрема діаграма на кожен із чотирьох сценаріїв, щонайменше один alt/opt/loopp у кожній, коректні активації, реалістичні назви викликів, учасники узгоджені з ER, кроки - зі сценаріями Gherkin.

## Ключове рішення — які альтернативи зважив і чому обрав цю (ADR):


1. **Учасники як сервіси й репозиторії над сутностями ER моделі** Відкинуто варіант Frontend / API / Database через те що він дає діаграму, яку неможливо звірити з моделлю даних. Прийнято InventoryController + GameService + репозиторії над Character, ItemCatalog/Item, InventoryPosition. InventoryController лишається єдиним учасником без відповідника з саме цим наміром.
2. **Кожна перевірка оформлена окреме повідомлення для явності** Відкинуто замовчування перевірок в діаграмах, ensureAdmin, existsCharacterInGame, isItemInGameCatalogs показані викликами.

## Перевірка

- Кожен із чотирьох сценаріїв Завдання 2 має власну діаграму; сценарії в spec.md скопійовані з Завдання 2 без змін.
- Кожна діаграма містить щонайменше один alt; гілки відповідають крокам сценарію (таблиця в аудиті).
- Активації перевірені
- Кожен учасник, крім InventoryController, звірений із сутністю ER
- Синтаксис усіх діаграм перевірений рендером
